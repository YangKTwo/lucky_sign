# 今日幸运签 产品需求文档

| 项目 | 内容 |
| --- | --- |
| 产品名称 | 今日幸运签 Lucky Sign |
| 文档版本 | v1.0 |
| 产品形态 | Flutter 移动端与 Web 客户端 + Spring Boot 服务端 |
| 目标用户 | 需要轻量监督、共享日常目标的小圈子成员；圈主/管理员 |
| 核心场景 | 每日领取任务、完成打卡、在圈内获得反馈并建立连续习惯 |

## 1. 产品概述

今日幸运签是一款面向熟人小圈子的每日行动产品。系统每天为成员生成不同难度的幸运签任务；成员提交文字或图片凭证后，打卡会进入圈子动态，其他成员可评分、聊天和互相提醒。

产品不以公开社交传播为目标，而以“让一个小圈子更容易坚持同一件事”为目标。用户打开应用后，第一优先级应始终是明确今天是否需要完成任务，以及如何完成。

## 2. 目标与边界

### 2.1 产品目标

1. 让成员在 10 秒内知道今日任务、奖励和截止时间。
2. 将一次打卡的完成成本控制在文字或一张图片的提交成本内。
3. 让小圈子的回应、评分和 @ 提醒成为连续打卡的正反馈。
4. 支持管理员管理准入、异常账号和不当聊天内容。

### 2.2 非目标

1. 不做公开广场、推荐流或陌生人社交。
2. 不做复杂项目管理、任务协作或多层级组织。
3. 不将 AI 助手定位为替代真人关系的主要功能。
4. 不在客户端保存任何服务端密钥或管理凭证。

## 3. 用户与使用场景

| 角色 | 目标 | 高频场景 | 成功标准 |
| --- | --- | --- | --- |
| 圈子成员 | 每天完成一个可执行的小任务并维持连续性 | 早晨查看任务、晚上补打卡、查看圈友动态 | 完成率、连续天数、有效反馈数 |
| 活跃成员 | 及时关注圈子消息并回应 @ | 社区查看未读、跳转到被 @ 消息、给打卡评分 | 未读处理率、互动响应时效 |
| 圈主/管理员 | 保持圈子准入和内容秩序 | 审核注册、解锁账号、删除违规文本 | 审核时效、投诉/违规处理时效 |

## 4. 核心体验原则

1. **今天优先**：首页不让历史统计抢占“今天要做什么”。
2. **轻量提交**：打卡必须在一个底部面板内完成，文字与图片都可选。
3. **圈子可感知**：打卡后清楚告知已同步到社区，并让成员能看到回应与评分。
4. **状态可恢复**：未读、@我、过期会话、失败上传均有明确去向和重试方式。
5. **管理不打扰成员**：审核与删除操作在管理员专属上下文中出现，避免污染普通聊天路径。

## 5. 信息架构

```text
登录/注册
└─ 应用主导航
   ├─ 今日：幸运签、任务、打卡、连续天数、称号进度
   ├─ 社区：实时聊天、@我、未读、撤回
   ├─ 动态：朋友圈式图文发布、互动、本周榜与完整排行入口
   └─ 我的：个人资料、语言、提醒、账号安全、管理员审批入口
```

## 6. 功能需求

### 6.1 认证与准入

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 用户可用邮箱和密码登录 | 登录成功后保存会话并进入主导航 |
| FR-02 | 新用户使用邀请码提交注册 | 注册后显示“等待管理员通过”，未批准不可登录 |
| FR-03 | 访问令牌过期时自动使用刷新令牌续期 | 并发请求只触发一次刷新；失败时清会话并回登录页 |
| FR-04 | 管理员可通过或拒绝注册申请 | 通过后用户加入圈子，社区出现加入和欢迎消息 |

### 6.2 每日幸运签与打卡

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-10 | 成员可查看当天幸运签、任务难度、奖励、幸运星和截止倒计时 | 每日页面首屏完整展示这些信息 |
| FR-11 | 成员可提交文字和/或单张图片作为打卡凭证 | 文件仅允许 jpg/png/webp/gif，最大 5MB |
| FR-12 | 打卡成功后更新任务状态、积分、连续天数和称号进度 | 页面不需重启即可刷新为完成态 |
| FR-13 | 打卡动态进入所属圈子的聊天流 | 聊天动态包含任务、得分与可选凭证 |
| FR-14 | 成员可查看自己的历史与日历 | 空历史、加载失败和日期范围受限时均有明确状态 |

### 6.3 社区聊天与互动

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-20 | 支持按圈子实时接收和发送文本消息 | 新消息通过 WebSocket 到达，无连接时可用 REST 发送兜底 |
| FR-21 | 支持 @ 圈子成员和 @助手 | @我消息在离开聊天页时进入未读/@我队列；@助手异步返回回复 |
| FR-22 | 支持消息历史分页 | 初始加载 30 条，单次最多 50 条，顺序稳定 |
| FR-23 | 支持查看未读和跳转到最早未读或 @我消息 | 社区图标显示未读数量，聊天内显示跳转入口与分隔线 |
| FR-24 | 本人可在发送后 2 分钟内撤回文本消息 | 撤回后保留时间线位置，正文替换为“已撤回” |
| FR-25 | 管理员可软删除可管理消息 | 被删消息显示“管理员已删除”，不显示图片、@或打卡详情 |
| FR-26 | 成员可给圈友的打卡评分 | 不允许给自己评分；显示评分进度、均分与本人评分 |

### 6.4 积分、称号与排行

| 编号 | 需求 | 验收标准 |

### 6.5 圈子动态

| FR-36 | 成员可发布文字及最多 9 张图片 | 发布前可预览、删除和调整图片；空内容不可发布 |

## 7. 关键用户流程

### 7.1 日常打卡

```text
打开应用 -> 今日页查看任务/剩余时间 -> 点击“完成并分享”
-> 填写感受或添加照片 -> 提交 -> 成功反馈
-> 今日页切换完成态 + 社区出现打卡动态
```

### 7.2 处理 @我

```text
收到实时消息 -> 不在社区或未位于底部 -> 记录未读/@我
-> 导航角标与聊天跳转按钮出现 -> 点击跳转
-> 高亮目标消息 -> 已读状态持久化
```

### 7.3 消息撤回与管理

```text
长按本人文本消息 -> 显示“撤回”（两分钟内） -> 确认 -> 实时替换为已撤回
管理员长按可管理消息 -> 删除 -> 所有人实时看到“管理员已删除”
```

## 8. 业务规则

1. 所有圈子数据操作均需验证当前用户是该圈成员。
2. 账号处于休眠状态时不可发言或完成打卡。
3. 打卡图片最大 5MB，必须基于文件内容检测 MIME 类型。
4. 聊天文本最大 1000 字；消息历史单次最大 50 条。
5. 仅 `TEXT` 消息可由本人撤回，窗口为创建后 2 分钟。
6. `CHECKIN` 和 `SYSTEM` 消息不可被管理员删除。
7. 删除是软删除，保留消息 ID、创建时间和删除原因，以确保时间线稳定。
8. AI 助手只在启用且被提及时调用；调用在聊天事务提交后异步处理。

## 9. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 主要页面首次数据返回后应立即呈现；列表刷新不重复抖动；聊天历史分页避免整页重载 |
| 可用性 | 断网、上传失败、会话过期、权限拒绝均提供可理解的恢复动作 |
| 安全 | BCrypt 密码哈希、JWT access/refresh 分离、CORS 白名单、接口限流、生产密钥仅通过环境变量注入 |
| 隐私 | 客户端不得内置数据库、JWT、OSS 或 AI 密钥；上传图片仅在圈子上下文展示 |
| 可访问性 | 关键文本对比度至少 WCAG AA；状态不能仅依赖颜色；最小触控尺寸 Android 48dp / iOS 44pt |
| 兼容性 | Flutter 目标 Android、iOS、Web；WebSocket 需适配 HTTPS/WSS 反向代理 |

## 10. 运营与数据指标

| 指标 | 定义 | 作用 |
| --- | --- | --- |
| 日打卡率 | 当日完成任务成员 / 当日活跃成员 | 核心价值指标 |
| 连续 7 天留存 | 连续 7 天均完成至少一次的成员占比 | 习惯形成信号 |
| 首次打卡完成时间 | 新成员加入后到第一次成功打卡的时长 | 引导有效性 |
| 社区响应率 | 打卡后 24 小时内获得至少一次互动的比例 | 小圈子活跃度 |
| @我处理时长 | @我消息到被标记已读的中位时长 | 消息机制质量 |
| 管理处理时长 | 注册申请/举报产生到管理员决策的时长 | 圈子治理质量 |

## 11. 迭代优先级

### P0：当前稳定性

1. 为聊天撤回、管理员删除、软删除显示补齐后端单元/集成测试。
2. 在移动端 CI 增加 `flutter test`、静态分析和关键页面截图检查。
3. 迁移 V6 前执行数据库备份、Flyway validate 和生产灰度验证。

### P1：体验完善

1. 重构今日页和社区页，使任务完成与未读处理成为首屏动作。
2. 为圈主增加集中式审批与内容管理入口。
3. 把未读状态由单端本地记录升级为服务端按用户同步。

### P2：规模化前准备

1. 多实例时将 STOMP simple broker、限流桶、AI 配额迁至 Redis/消息系统。
2. 定时任务改为具备分布式锁或独立调度器的实现。
3. 为 OSS 图片配置 CDN、生命周期和内容审核策略。
